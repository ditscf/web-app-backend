# Identity model

Persistence model for V1 identity, authentication, and assignments. The Prisma schema in `prisma/schema.prisma` is this model. Registration and the two approval steps are implemented in `src/membership`. Other workflows that change these rows are not implemented yet.

Primary keys are UUID v7 values generated by Prisma Client. A raw SQL insert must supply the id itself. The database column has no default.

## Why the records are separate

| Record | What it is | Why it is not merged |
| --- | --- | --- |
| Person | The human record and unique email | Exists from registration through graduation |
| Application | One registration attempt | Expires after 48 hours and can be repeated without creating a member |
| ApplicationDecision | The General Secretary step or the Vice General Secretary step | One flag cannot require two different approvers |
| Membership | Active Member or Associate, plus Fellowship ID | Begins only at approval |
| Account | Permission to attempt sign-in | Created at approval and disabled for Associates. Stores no password |
| Session | One signed-in browser | Points at the account only |
| LoginCode | Hashed one-time email code | Exists only long enough to create a session |
| AuthEmail | Record that an auth email was attempted | Does not store the code or the body |
| FellowshipOfficeAssignment | Chairman, Vice Chairman, GS, VGS, or Treasurer for one year | Not a permanent role on the person |
| MinistryLeaderAssignment | Current or historical leader of one ministry | Not a fellowship office |
| MinistryMembership | A person's current or past participation in one ministry | A person can be in several ministries, and history is kept |
| EventRoleAssignment | Event Chairman, Event Treasurer, or Event Secretary for one event | Does not grant fellowship authority |

## Registration and approval

An applicant submits profile fields on `Person` and a `PENDING` application. `expiresAt` is exactly 48 hours after `submittedAt`. There is no password column.

A person may have only one `PENDING` application. After expiry, a new attempt is a new application row. A person who already has a membership cannot start another application.

`ApplicationDecision` allows one row per step. A second unique constraint on application and approver rejects the same person recording both steps. The application becomes `APPROVED` only when both rows exist. That transition creates `Membership`, generates `fellowshipId`, creates an enabled `Account`, and records an activation `AuthEmail`. The activation email does not create a session.

`fellowshipId` is allocated by the rule in `docs/design/fellowship-id.md`. It is eight digits: the fellowship year's last two digits, the day of birth, and a four-digit sequence, for example `26160001`.

## Sign-in records

`LoginCode.codeHash` and `Session.tokenHash` store hashes only. Sessions cascade away with the account if an account row is removed. People, memberships, and approval decisions are protected with `ON DELETE RESTRICT` so history is not removed by a cascading delete.

An account with status `DISABLED` cannot receive a login code. Graduation sets that status. The person and membership remain.

## Fellowship years and offices

`FellowshipYear.operativeSlot` is `1` while the year is `OPEN` or `CLOSED`, and `null` when it is `ARCHIVED`. The column is unique. PostgreSQL allows many nulls, so archived years accumulate, and only one year can hold the operative slot. Writers must change the slot in the same update as the status.

`FellowshipOfficeAssignment.effectiveTo` null means the current holder. Replacing an officer sets `effectiveTo` on the old row. The partial unique indexes enforce:

- one current holder per office per year
- one person cannot currently be both General Secretary and Vice General Secretary in the same year

The same person may hold an office again in a later year, as a new row. The same person may hold another office beside GS or VGS.

The first year and its officers are created by the operator script described in `docs/design/handover.md`. There is no election table and no in-app administrator. A later year attaches existing members by email. Ministries are not part of that script.

## Ministry and event scope

`Ministry` and `Event` exist so leadership assignments have real parents. Ministry names are predefined seed data loaded by `npm run seed:ministries`. Event venue, participants, and event finance are not in this schema.

`MinistryMembership` rows are first created by onboarding. A null `effectiveTo` is current. A partial unique index allows one current row per person and ministry. `Membership.onboardedAt` records that onboarding was submitted. After that, the member cannot change their own ministries. See `docs/design/onboarding.md`.

An event belongs to the fellowship year in which it is created. Ministry leadership is not stored against a fellowship year. A closed year still stops ministry-leader operations through the authorization policy.

A null `effectiveTo` is the current ministry leader or the current event-role holder. Partial unique indexes allow one current leader per ministry and one current holder per event role.

## Assumptions carried into the schema

- At most one fellowship year is operative.
- An event belongs to one fellowship year.
- Ministry leadership is scoped to the ministry, not stored as a year-bound office.
- Email is stored lowercase. The unique constraint is case-sensitive.
- The activation email and the login code are different `AuthEmail` types. Only a verified login code creates a session.
